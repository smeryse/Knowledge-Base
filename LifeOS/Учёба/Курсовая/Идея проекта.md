# Идея курсовой работы: Персональная система управления продуктовыми запасами с LLM-нормализацией

---

## Проблематика

Современный человек сталкивается с рядом бытовых проблем при управлении питанием:

- **Нет единого учёта**: продукты покупаются импульсивно — дома уже есть, но дублируется.
- **Просрочка и порча**: отсутствует контроль сроков годности — еда выбрасывается.
- **Нет истории цен**: невозможно оценить, где покупать выгоднее.
- **Трение при вводе**: вести базу продуктов вручную — слишком трудоёмко.

Существующие решения (Trello, Google Sheets, Notion, списки покупок в мессенджерах) решают лишь отдельные задачи, не образуя замкнутого цикла: **купил → учёл → приготовил → списал**.

---

## Идея проекта

Разработать **персональную ERP-систему учёта продуктов питания**, построенную как набор автоматизированных скриптов внутри Obsidian (note-taking платформа). Система охватывает полный жизненный цикл продуктов:

```
Покупка → Добавление в хранилище → Приготовление → Списание
```

Ключевая особенность — **автоматизация ввода данных через несколько каналов**:
- Сканирование штрихкодов с подтягиванием данных из глобальных баз (Open Food Facts, Go-UPC)
- Импорт электронных чеков по QR-коду (proverkacheka.com, ФНС)
- OCR-распознавание бумажных чеков (Tesseract)
- Ручной ввод с автодополнением

Данные агрегируются из внешних источников, а **LLM (Large Language Model) используется для нормализации и синтеза структурированной записи товара** из множества неструктурированных кандидатов.

---

## Цель работы

Создать функционирующую систему персонального учёта продуктов, минимизирующую ручной ввод за счёт автоматического распознавания (штрихкоды, чеки, QR) и LLM-нормализации данных.

---

## Задачи

1. **Спроектировать модель данных**: сущности (товары, чеки, категории, магазины, запасы, рецепты), их атрибуты и связи.
2. **Реализовать конвейер сканирования штрихкодов**: поиск товара в локальной БД → параллельный опрос внешних API (Open Food Facts, Go-UPC, barcode-list.ru, веб-поиск) → дедупликация кандидатов.
3. **Реализовать LLM-нормализатор**: модуль, который принимает сырые данные из нескольких источников и возвращает единую структурированную запись (название, бренд, категория, фасовка, срок годности) по заданной JSON-схеме.
4. **Реализовать импорт чеков по QR**: интеграция с API proverkacheka.com для автоматического получения и разбора электронных чеков.
5. **Реализовать ручной и OCR-ввод**: создание позиций и чеков через диалоги и распознавание изображений.
6. **Реализовать учёт запасов**: Pantry (что есть дома), Shopping List (список покупок), Cooking Log (журнал готовки со списанием ингредиентов).
7. **Провести апробацию**: внести реальные покупки за N недель и оценить качество автоматического распознавания.

---

## Объект и предмет исследования

- **Объект исследования**: процессы учёта и планирования продуктовых запасов в домашнем хозяйстве.
- **Предмет исследования**: методы автоматизации ввода и нормализации данных о продуктах с использованием LLM и внешних API.

## Методы и технологии

| Компонент | Технология |
|---|---|
| Среда выполнения | Obsidian + Templater plugin |
| Язык реализации | JavaScript (ES6+) |
| Формат данных | Markdown + YAML frontmatter |
| OCR | Tesseract (локальный бинарный движок) |
| Внешние API | Open Food Facts, Go-UPC, barcode-list.ru, proverkacheka.com, ФНС |
| LLM | Локально: LM Studio/Ollama; Облачно: Groq (Llama 3.1, Qwen 2.5) |
| Веб-поиск | DuckDuckGo, Bing (как fallback-источники штрихкодов) |
| Версионирование | Git |

Архитектура системы — **file-as-database**: каждая папка — таблица, каждый Markdown-файл — запись, YAML frontmatter — поля, wikilinks — внешние ключи. База данных версионируется через Git, не требует отдельного сервера.

## Архитектура решения

### Модель данных (основные сущности)

- **Products** — справочник товаров (штрихкод, название, бренд, категория, единица измерения, срок годности)
- **Receipts** — чеки (дата, магазин, сумма)
- **Receipt Items** — позиции чеков (продукт, количество, цена, скидка)
- **Pantry Items** — текущие запасы (продукт, остаток, срок годности)
- **Categories** — иерархия категорий
- **Stores** — справочник магазинов
- **Recipes** — рецепты (нормализованы на 1 порцию)
- **Shopping Items** — список покупок

### Конвейер LLM-нормализации

1. Пользователь вводит штрихкод
2. Система ищет в локальной БД → если не найдено, запускает параллельный опрос 3-5 внешних источников
3. Все ответы собираются в массив кандидатов (разные названия, разные форматы)
4. Кандидаты отправляются LLM с промптом:
   > "Синтезируй единую структурированную запись из следующих источников. Предпочти русские названия. Извлеки размер упаковки. Оцени уверенность."
5. LLM возвращает JSON-объект по утверждённой схеме
6. Пользователь подтверждает или корректирует → запись сохраняется в Products

## Ожидаемые результаты

1. **Готовая система** — полноценное Obsidian-приложение для учёта продуктов с четырьмя каналами ввода данных.
2. **Методика LLM-нормализации** — алгоритм синтеза структурированных данных из множества неструктурированных источников с оценкой уверенности.
3. **Оценка качества** — статистика успешного автоматического распознавания товаров по штрихкодам (цель: >80% без ручного вмешательства).
4. **Отчёт по апробации** — анализ внедрения системы в реальное использование в течение 1-2 месяцев.

## Почему это актуально для курсовой

- **Прикладная значимость**: решает реальную бытовую проблему — можно использовать после сдачи.
- **Full-stack охват**: работа затрагивает проектирование БД, интеграцию с внешними API, работу с LLM, UI/UX в рамках Obsidian.
- **Современные технологии**: LLM, OCR, REST API, file-as-database архитектура.
- **Измеримый результат**: можно оценить процент успешного распознавания, время ввода одной покупки.
- **Возможность развития**: диплом — веб-приложение или телеграм-бот с тем же бэкендом.
