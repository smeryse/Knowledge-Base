## 1. Инфологическая модель (ER-диаграмма Чена)
**Сущности:**
- Лаборатория (id, название, корпус, телефон)
- Сотрудник (id, ФИО, email, телефон, дата_рождения)
- Должность (id, название, оклад)
- Научный_проект (id, название, бюджет, дата_начала, дата_окончания)
- Грант (id, название, сумма, источник, дата_получения)
- Публикация (id, название, дата, тип)
- Оборудование (id, название, инвентарный_номер, стоимость, дата_покупки)
- Заявка_на_оборудование (id, дата, статус, обоснование)

**Связи:**
- Сотрудник (1) работает_в (0..M) Лаборатория
- Научный_проект (1) ведётся_в (0..M) Лаборатория

- Сотрудник (1) подал (0..M) Заявка_на_оборудование
- Оборудование (1) включено_в (0..M) Заявка_на_оборудование

## 2. Физическая модель БД
Физическая модель реляционной базы данных включает набор отношений, соответствующих сущностям предметной области, с указанием первичных и внешних ключей. В рамках данной модели определены следующие таблицы: 
Laboratory(laboratory_id PK, name, location, foundation_year), 
Position(position_id PK, title, salary), 
Employee(employee_id PK, last_name, first_name, email UK, phone, birth_date, laboratory_id FK, position_id FK), 
Grant(grant_id PK, name, amount, source, received_date), 
ScientificProject(project_id PK, name, budget, start_date, end_date, grant_id FK), 
Publication(publication_id PK, name, date, type, project_id FK), 
Equipment(equipment_id PK, name, inventory_number UK, cost, purchase_date, laboratory_id FK), 
EquipmentRequest(request_id PK, date, status, justification, employee_id FK, equipment_id FK), 
EmployeeProject(employee_id PK FK, project_id PK FK, role, participation_start). 
Данная структура полностью отражает связи ER-модели и реализует все отношения в виде реляционных таблиц с устранением связи M:N через ассоциативную сущность EmployeeProject.

Функциональные зависимости в данной предметной области определяются первичными ключами сущностей. Для каждой таблицы выполняется зависимость вида PK → все неключевые атрибуты. Например, employee_id функционально определяет личные данные сотрудника и его связи с лабораторией и должностью, laboratory_id определяет характеристики лаборатории, position_id определяет название должности и оклад, project_id определяет параметры научного проекта, grant_id определяет характеристики гранта. В связующей сущности EmployeeProject составной ключ (employee_id, project_id) определяет только атрибуты участия, такие как роль и дата участия, и не определяет данные исходных сущностей.

Проверка второй нормальной формы показывает отсутствие частичных функциональных зависимостей. Единственной сущностью с составным ключом является EmployeeProject, и все её неключевые атрибуты зависят от полного ключа (employee_id, project_id). Отсутствуют зависимости вида employee_id → role или project_id → role, что исключает нарушение 2НФ. Проверка третьей нормальной формы показывает отсутствие транзитивных зависимостей неключевых атрибутов. Все атрибуты зависят только от первичного ключа своей сущности, а связанные характеристики вынесены в отдельные таблицы (например, данные лаборатории не хранятся в Employee, а данные должности не дублируются в других сущностях). Таким образом отсутствуют зависимости вида PK → non-key → non-key.

Следовательно, все отношения находятся в третьей нормальной форме, так как выполнены условия 1НФ (атомарность атрибутов), 2НФ (отсутствие частичных зависимостей) и 3НФ (отсутствие транзитивных зависимостей). Модель корректно нормализована и готова к реализации в реляционной СУБД без аномалий вставки, обновления и удаления.

# 4. Необходимость индексов

Первичные ключи автоматически индексируются СУБД.

Дополнительные индексы необходимы для ускорения соединений таблиц по внешним ключам:

```sql
CREATE INDEX idx_employee_lab
ON Employee(laboratory_id);

CREATE INDEX idx_project_grant
ON Project(grant_id);

CREATE INDEX idx_employee_project_emp
ON Employee_Project(employee_id);

CREATE INDEX idx_employee_project_proj
ON Employee_Project(project_id);
```

Обоснование:

- таблицы Employee и Project участвуют в соединениях с другими таблицами;
    
- таблица Employee_Project реализует связь M:N и будет активно использоваться в JOIN-запросах;
    
- отсутствие индексов приведёт к полному сканированию таблиц при росте объёма данных.

# 5. SQL-команды управления данными

Для **каждой таблицы** должны быть:

- INSERT (2–3 записи);
    
- UPDATE по первичному ключу;
    
- DELETE по первичному ключу.
    

Например для Employee:

```sql
INSERT INTO Employee
(last_name, first_name, email, hire_date, laboratory_id, position_id)
VALUES
('Иванов','Иван','ivanov@uni.ru','2022-02-01',1,1),
('Петров','Пётр','petrov@uni.ru','2021-09-01',1,2);
```

```sql
UPDATE Employee
SET
    last_name='Сидоров',
    first_name='Сергей',
    email='sidorov@uni.ru',
    hire_date='2023-01-01',
    laboratory_id=2,
    position_id=2
WHERE employee_id=1;
```

```sql
DELETE FROM Employee
WHERE employee_id=2;
```

Аналогичные команды оформляются для остальных таблиц.

# 8. Сложный SQL-запрос

Вывести проекты, количество участников проекта и общий объём финансирования гранта.

```sql
SELECT
    p.project_name AS project,
    COUNT(ep.employee_id) AS participant_count,
    g.amount AS grant_amount

FROM Project p

JOIN Employee_Project ep
    ON p.project_id = ep.project_id

JOIN Grants g
    ON p.grant_id = g.grant_id

GROUP BY
    p.project_id,
    p.project_name,
    g.amount

ORDER BY participant_count DESC;
```

# 9. Код на C#

Код не должен содержать новый произвольный запрос.

Он должен выполнять запрос из пункта 8 и выводить его результат.

Также параметризованные команды могут использоваться для выполнения команд INSERT, UPDATE и DELETE, разработанных в пункте 5.
