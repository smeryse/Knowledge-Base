## 2. Физическая модель БД


ER-модель описывает структуру предметной области на концептуальном уровне, а физическая модель преобразует её в реляционную структуру, пригодную для реализации в СУБД с учётом ограничений реляционной модели.

Единственным изменением при переходе от ER-модели к реляционной является замена связи M:N между сотрудниками и проектами на ассоциативную таблицу EmployeeProject, что обеспечивает нормализацию и исключает аномалии вставки и удаления.

Нулевая нормальная форма (0НФ) соответствует исходному представлению данных, где информация может храниться в виде неструктурированных или слабо структурированных записей, допускающих повторяющиеся группы и множественные значения в одном атрибуте. В контексте научной лаборатории это может выглядеть как единая запись о проекте, где в одном поле перечислены все сотрудники проекта списком, например: project_id, project_name и employee_list, где employee_list содержит сразу несколько сотрудников. Такая структура нарушает базовые принципы реляционной модели, так как данные не атомарны и присутствуют повторяющиеся группы.

Переход к первой нормальной форме (1НФ) заключается в устранении повторяющихся групп и приведении всех атрибутов к атомарным значениям. Это означает, что каждое поле должно содержать только одно значение, а не список. В нашем примере это приводит к тому, что связь между сотрудниками и проектами начинает представляться через отдельные строки: один проект — один сотрудник на строку. В результате появляется таблица вида project_id, project_name, employee_id, employee_name, где одна и та же информация о проекте повторяется для каждого сотрудника. Хотя данные становятся атомарными, возникает избыточность и повторение данных, а также предпосылки для аномалий обновления.

Вторая нормальная форма (2НФ) устраняет частичные зависимости неключевых атрибутов от части составного ключа. В нашем примере ключом является комбинация project_id и employee_id, но project_name зависит только от project_id, а employee_name зависит только от employee_id. Это означает, что данные о проекте и сотруднике не должны храниться в одной таблице. Поэтому выполняется декомпозиция на три отношения: Project с атрибутами project_id и project_name, Employee с атрибутами employee_id и employee_name, и связующую таблицу EmployeeProject с ключом employee_id и project_id. После этого перехода устраняется избыточность и достигается третья нормальная форма в базовом виде, так как в 3НФ дополнительно проверяется отсутствие транзитивных зависимостей неключевых атрибутов от ключа, что в полученной структуре обеспечивается разделением сущностей и хранением каждой группы фактов в своей таблице.

В данной предметной области функциональные зависимости задаются ключами сущностей. В каждой таблице первичный ключ однозначно определяет все неключевые атрибуты: например, employee_id определяет ФИО, email, телефон и дату рождения сотрудника, а laboratory_id определяет название, корпус и телефон лаборатории. Аналогично, project_id определяет данные научного проекта, а grant_id — параметры гранта.

Связи между сущностями через внешние ключи не создают функциональных зависимостей между неключевыми атрибутами разных таблиц. Например, employee_id не определяет данные лаборатории напрямую, так как они зависят только от laboratory_id. Это исключает транзитивные зависимости в корректно нормализованной модели.

Для связей M:N, таких как сотрудник–проект, используется связующая таблица, где составной ключ (employee_id, project_id) определяет только атрибуты участия, например роль, и не наследует данные из других сущностей. Таким образом, все функциональные зависимости строго соответствуют ключам и модель находится в нормализованном виде.```

Частичные зависимости отсутствуют, потому что во всех сущностях с составным ключом неключевые атрибуты зависят от всего ключа целиком. Единственная такая сущность — Сотрудник_Проект с ключом (employee_id, project_id). Её неключевые атрибуты, такие как роль и дата_участия, зависят от комбинации сотрудника и проекта одновременно, а не от одного из них по отдельности. Это исключает частичные зависимости вида employee_id → роль или project_id → роль, которые нарушали бы 2НФ.

Транзитивные зависимости отсутствуют, так как неключевые атрибуты не зависят друг от друга через промежуточные неключевые поля внутри одной сущности. Например, в сущности Сотрудник атрибут employee_id определяет laboratory_id и position_id, но эти значения не раскрываются внутри таблицы сотрудника в виде названия лаборатории или оклада должности. Соответственно, не возникает цепочек вида employee_id → laboratory_id → название лаборатории внутри одной таблицы, так как данные лаборатории и должности вынесены в отдельные сущности.

Таким образом, каждая сущность содержит только атомарные атрибуты, зависящие строго от своего первичного ключа, а связи между сущностями реализованы через внешние ключи. Это обеспечивает отсутствие частичных и транзитивных зависимостей и соответствие модели третьей нормальной форме.

# 4. Необходимость индексов

Первичные ключи автоматически индексируются СУБД.

Дополнительные индексы необходимы для ускорения соединений таблиц по внешним ключам:

```sql
CREATE INDEX idx_employee_lab
ON Employee(laboratory_id);

CREATE INDEX idx_project_grant
ON Project(grant_id);

CREATE INDEX idx_employee_project_emp
ON Employee_Project(employee_id);

CREATE INDEX idx_employee_project_proj
ON Employee_Project(project_id);
```

Обоснование:

- таблицы Employee и Project участвуют в соединениях с другими таблицами;
    
- таблица Employee_Project реализует связь M:N и будет активно использоваться в JOIN-запросах;
    
- отсутствие индексов приведёт к полному сканированию таблиц при росте объёма данных.

# 5. SQL-команды управления данными

Для **каждой таблицы** должны быть:

- INSERT (2–3 записи);
    
- UPDATE по первичному ключу;
    
- DELETE по первичному ключу.
    

Например для Employee:

```sql
INSERT INTO Employee
(last_name, first_name, email, hire_date, laboratory_id, position_id)
VALUES
('Иванов','Иван','ivanov@uni.ru','2022-02-01',1,1),
('Петров','Пётр','petrov@uni.ru','2021-09-01',1,2);
```

```sql
UPDATE Employee
SET
    last_name='Сидоров',
    first_name='Сергей',
    email='sidorov@uni.ru',
    hire_date='2023-01-01',
    laboratory_id=2,
    position_id=2
WHERE employee_id=1;
```

```sql
DELETE FROM Employee
WHERE employee_id=2;
```

Аналогичные команды оформляются для остальных таблиц.

# 8. Сложный SQL-запрос

Вывести проекты, количество участников проекта и общий объём финансирования гранта.

```sql
SELECT
    p.project_name AS project,
    COUNT(ep.employee_id) AS participant_count,
    g.amount AS grant_amount

FROM Project p

JOIN Employee_Project ep
    ON p.project_id = ep.project_id

JOIN Grants g
    ON p.grant_id = g.grant_id

GROUP BY
    p.project_id,
    p.project_name,
    g.amount

ORDER BY participant_count DESC;
```
